# Chapter 11 — Profile-Guided Optimization (PGO)

## Goal

Understand how Go can use a real CPU profile to guide compiler optimizations.

The key idea:

```text
Real workload
    ↓
CPU profile
    ↓
PGO profile
    ↓
Compiler optimization
    ↓
Optimized binary
```

PGO is different from manually optimizing one function after reading a benchmark.

## What You Should Learn

- What PGO is.
- Why production profiles can contain information the compiler cannot know from source alone.
- How a CPU profile becomes a PGO input.
- How to build a Go binary with PGO.
- Why representative profiles matter.
- Why PGO is not a replacement for benchmarking or profiling.
- What kinds of optimization decisions PGO can influence.
- Why small benchmark wins do not automatically justify PGO in production.

## Production Problem

Suppose a service has already been reasonably optimized.

You profile production and discover a stable workload:

```text
hot path
    ↓
request parsing
    ↓
validation
    ↓
business logic
    ↓
encoding
```

The compiler already performs many optimizations automatically.

But the compiler does not know your application's **real production execution frequencies** as well as a representative profile does.

PGO lets the compiler use that profile information.

## Concept

Without PGO:

```text
source code
    ↓
compiler
    ↓
binary
```

With PGO:

```text
source code
    +
representative CPU profile
    ↓
compiler
    ↓
profile-guided binary
```

The compiler can make optimization decisions based on where the program is actually hot.

A useful mental model:

> PGO does not tell the compiler what your program means. It tells the compiler what parts of the program are important under a representative workload.

## PGO Is Not Runtime Tuning

Do not confuse:

```text
GOGC
GOMEMLIMIT
```

with:

```text
PGO
```

GOGC/GOMEMLIMIT affect runtime memory/GC behavior.

PGO affects **compiler-generated code**.

```text
Runtime tuning
    → program behavior while running

PGO
    → how the compiler builds the program
```

## PGO Is Not a Magic Speed Switch

PGO can improve performance, but:

- gains depend on workload;
- profiles must represent real usage;
- not every application gets a large improvement;
- a profile from the wrong workload can guide optimization in the wrong direction.

Therefore:

> The quality of the profile matters.

## Representative Profile

Imagine a service has:

```text
80% normal API traffic
15% admin traffic
5% background jobs
```

If your profile contains only background jobs, PGO may optimize the wrong workload.

A representative profile should capture the execution behavior you actually care about.

For a production service, this generally means collecting a CPU profile during representative traffic rather than inventing a synthetic profile.

## Experiment

This chapter includes a small HTTP application with a hot path:

```go
func score(data []byte) int {
    total := 0

    for _, b := range data {
        total += int(b)
    }

    return total
}
```

The handler repeatedly calls the hot path.

First build normally:

```bash
go build -o app-normal .
```

Run it:

```bash
./app-normal
```

Then generate representative traffic:

```bash
curl http://localhost:8080/score
```

For a real service, you would collect a CPU profile while representative traffic is running.

For learning, you can use the profile generated by the benchmark.

## Generate a CPU Profile

Run:

```bash
go test -bench=BenchmarkScore -cpuprofile=cpu.out
```

Inspect it:

```bash
go tool pprof -top cpu.out
```

You should be able to identify the hot path.

## Build With PGO

Go can consume a CPU profile as the PGO input.

Build with:

```bash
go build -pgo=cpu.out -o app-pgo .
```

Build normally for comparison:

```bash
go build -pgo=off -o app-normal .
```

The exact profile should be representative of the program's intended workload.

## Compare

Benchmark the program:

```bash
go test -bench=BenchmarkScore -benchmem
```

For binary-level comparisons, benchmark the relevant application path under the same workload.

Compare:

```text
normal build
vs
PGO build
```

Keep the workload identical.

Do not compare unrelated runs and call the difference a PGO improvement.

## Why PGO Can Help

Consider:

```text
Caller A → function X
Caller B → function X
Caller C → function X
```

The source code alone does not tell the compiler how often each caller matters in your real workload.

A profile can show:

```text
Caller A → very hot
Caller B → rarely used
Caller C → almost never used
```

The compiler can use profile information when making optimization decisions around hot paths.

One important example is **inlining**.

PGO can help the compiler make better decisions about which call sites are worth optimizing based on actual execution frequency.

## PGO and Inlining

Recall the previous chapters:

```text
buildReport (inline)
```

Inlining means the compiler incorporated a function into its caller.

PGO can provide execution-frequency information that helps the compiler prioritize optimization of hot call paths.

Mental model:

```text
Without profile:
    "Which call sites look important?"

With profile:
    "Which call sites are actually hot?"
```

The compiler still decides what transformation is valid.

PGO is guidance, not a manual optimization script.

## PGO and Memory

This is inside `03-memory-performance`, but PGO itself is not primarily a memory profiler.

A CPU profile is normally used as the PGO input.

PGO may indirectly affect memory behavior because compiler decisions can change:

- inlining;
- generated code;
- allocation-related optimization opportunities;
- escape-analysis outcomes in some cases.

But do not use PGO as a substitute for:

```text
heap profiling
allocation profiling
retention analysis
```

If you have a memory leak, PGO is not the first tool to reach for.

## Production Workflow

A mature workflow looks like:

```text
Production
    ↓
Observe performance problem
    ↓
CPU profile
    ↓
Find stable hot paths
    ↓
Collect representative profile
    ↓
Build with PGO
    ↓
Benchmark / load test
    ↓
Canary
    ↓
Compare production metrics
    ↓
Keep or revert
```

The important part is that PGO comes **after measurement**.

## Common Mistakes

### 1. Using a non-representative profile

If the profile represents the wrong workload, PGO may optimize the wrong paths.

### 2. Expecting huge speedups

PGO is not guaranteed to produce dramatic improvements.

### 3. Replacing benchmarks with PGO

You still need controlled benchmarks to measure changes.

### 4. Replacing profiling with PGO

You still need profiles to understand production behavior.

### 5. Using a stale profile

If the application changed substantially, an old profile may no longer represent the current hot paths.

### 6. Optimizing before finding a stable hot path

PGO is most useful when there is a meaningful, repeatable workload.

## What To Observe

When evaluating PGO, compare:

```text
throughput
latency
CPU utilization
benchmark ns/op
binary behavior
allocation metrics
```

Do not look only at one benchmark number.

A useful result is:

```text
CPU ↓
latency ↓
throughput ↑
memory stable
```

A suspicious result is:

```text
benchmark ↑
but production latency unchanged
```

That may mean the benchmark does not represent production.

## Commands

Generate CPU profile:

```bash
go test -bench=BenchmarkScore -cpuprofile=cpu.out
```

Inspect:

```bash
go tool pprof -top cpu.out
```

Normal build:

```bash
go build -pgo=off -o app-normal .
```

PGO build:

```bash
go build -pgo=cpu.out -o app-pgo .
```

Check build help:

```bash
go help build
```

## Summary

PGO is:

```text
real workload
    ↓
profile
    ↓
compiler guidance
    ↓
better optimization decisions
```

Remember:

1. PGO guides compiler optimization using profile data.
2. PGO is different from runtime settings such as GOGC and GOMEMLIMIT.
3. Representative profiles are critical.
4. PGO is not a replacement for benchmarking.
5. PGO is not a replacement for profiling.
6. PGO can help optimization decisions such as hot-path inlining.
7. PGO is most useful after you already understand the application's important workloads.
8. Validate PGO builds with controlled benchmarks and real production metrics.

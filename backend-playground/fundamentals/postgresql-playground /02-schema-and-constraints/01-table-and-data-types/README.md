# 01 — Table and Data Types

## Goal

Learn how to design PostgreSQL tables and choose practical data types for production backend systems.

Focus:

- `CREATE TABLE`
- columns
- common PostgreSQL data types
- `TEXT`
- integer and numeric types
- `BOOLEAN`
- `DATE`
- `TIMESTAMP` vs `TIMESTAMPTZ`
- UUID
- identity columns
- `JSONB`
- `ARRAY`
- NULL and defaults
- choosing types based on domain meaning
- schema/application boundaries

The goal is:

> **Make the database schema represent the data correctly from the beginning.**

---

## 1. Table Mental Model

A table represents a domain concept.

Examples:

```text
users
orders
products
payments
comments
```

A row should represent one clear thing.

For example:

```text
users
→ one row = one user

orders
→ one row = one order

order_items
→ one row = one item in an order
```

Before designing columns, define what one row means.

---

## 2. Basic CREATE TABLE

```sql
CREATE TABLE users (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name TEXT NOT NULL,
    email TEXT NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

A column definition generally contains:

```text
name
+
data type
+
optional constraints
+
optional default
```

Schema design starts with the domain, not with random fields.

---

## 3. Data Types Represent Meaning

A data type communicates:

```text
what the value represents
what values can be represented
what operations make sense
```

Examples:

```text
active       → BOOLEAN
price        → NUMERIC
created_at   → TIMESTAMPTZ
birth_date   → DATE
user_id      → BIGINT / UUID
name         → TEXT
```

Choose types based on domain meaning.

---

## 4. TEXT

PostgreSQL commonly uses:

```sql
TEXT
```

for strings.

Typical uses:

```text
name
title
description
message
address
business code
external identifier
```

For many application strings, `TEXT` is the simplest practical choice.

---

## 5. TEXT vs VARCHAR

PostgreSQL supports:

```text
TEXT
VARCHAR
VARCHAR(n)
```

Do not automatically use:

```sql
VARCHAR(255)
```

because it is traditional.

Use a length restriction when the domain has a meaningful limit.

Example:

```sql
code TEXT CHECK (char_length(code) <= 20)
```

The question is:

> Is this limit a real business rule?

---

## 6. Empty String vs NULL

These are different:

```text
NULL
''
' '
```

They can represent different states.

For example:

```text
NULL
→ no value

''
→ explicitly empty string

' '
→ whitespace
```

If a value is required:

```sql
name TEXT NOT NULL
```

is usually preferable to accepting NULL and relying only on application validation.

---

## 7. Integer Types

Common integer types:

```text
SMALLINT
INTEGER
BIGINT
```

The practical difference is their supported range.

Choose based on the domain:

```text
small bounded value → SMALLINT
normal integer      → INTEGER
large IDs/counters  → BIGINT
```

The important rule is intentional choice and consistency.

---

## 8. BIGINT IDs

A common production convention:

```sql
id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY
```

The database generates the ID.

Example:

```sql
CREATE TABLE users (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name TEXT NOT NULL
);
```

The exact ID type is an architectural decision.

---

## 9. Identity Columns

Modern PostgreSQL supports identity columns:

```sql
id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY
```

Then:

```sql
INSERT INTO users (name)
VALUES ('Agus')
RETURNING id;
```

The database generates the ID and returns it.

---

## 10. GENERATED ALWAYS vs BY DEFAULT

You may encounter:

```sql
GENERATED ALWAYS AS IDENTITY
```

and:

```sql
GENERATED BY DEFAULT AS IDENTITY
```

The practical difference concerns whether explicit values are normally allowed.

The main design question is:

> Who owns ID generation?

Pick a consistent convention.

---

## 11. SERIAL and BIGSERIAL

Existing PostgreSQL systems may use:

```sql
SERIAL
BIGSERIAL
```

Recognize them when maintaining older schemas.

For new designs, identity columns are generally clearer:

```sql
BIGINT GENERATED ALWAYS AS IDENTITY
```

Do not rewrite a working production schema merely to replace `SERIAL`.

---

## 12. UUID

PostgreSQL supports:

```sql
UUID
```

Example:

```sql
CREATE TABLE users (
    id UUID PRIMARY KEY,
    name TEXT NOT NULL
);
```

UUIDs can be useful when identifiers need global uniqueness or independent generation.

---

## 13. Numeric ID vs UUID

Both can be production-ready.

Numeric IDs:

```text
simple
compact
common
```

UUIDs:

```text
globally unique
useful across distributed systems
can be generated independently
```

Choose based on:

```text
architecture
existing conventions
distributed creation
API design
operational requirements
```

UUID does not automatically make an API secure.

---

## 14. BOOLEAN

Use:

```sql
BOOLEAN
```

for genuine true/false state.

Example:

```sql
active BOOLEAN NOT NULL DEFAULT true
```

Avoid string flags such as:

```text
'yes'
'no'
'active'
'inactive'
```

when only two states exist.

---

## 15. When BOOLEAN Is Not Enough

Payment state might be:

```text
pending
paid
failed
refunded
```

A boolean cannot represent all four states cleanly.

A status field is more appropriate:

```sql
status TEXT NOT NULL
```

with appropriate constraints later.

Model the real state machine.

---

## 16. Nullable BOOLEAN

A nullable boolean has:

```text
TRUE
FALSE
NULL
```

That can be valid if the third state has real meaning.

For a simple flag:

```sql
active BOOLEAN NOT NULL DEFAULT true
```

is easier to reason about.

---

## 17. DATE

Use:

```sql
DATE
```

when only a calendar date matters.

Example:

```sql
birth_date DATE
```

Value:

```text
2026-09-02
```

There is no reason to invent a time if the domain does not have one.

---

## 18. TIMESTAMP

`TIMESTAMP` represents date and time without timezone information.

Use it when the domain genuinely needs a timezone-independent/local wall-clock value.

Be careful using it for distributed events.

---

## 19. TIMESTAMPTZ

For an event representing an instant in time:

```sql
TIMESTAMPTZ
```

is a common production choice.

Example:

```sql
created_at TIMESTAMPTZ NOT NULL DEFAULT now()
```

Typical columns:

```text
created_at
updated_at
paid_at
published_at
deleted_at
```

---

## 20. DATE vs TIMESTAMP vs TIMESTAMPTZ

Mental model:

```text
DATE
→ calendar date

TIMESTAMP
→ local date/time without timezone semantics

TIMESTAMPTZ
→ instant in time
```

For backend event timestamps, `TIMESTAMPTZ` is often the safest default.

---

## 21. Timezone Is a Domain Decision

Compare:

```text
store opens at 09:00
```

with:

```text
order created at 09:00 UTC
```

The first can be a local wall-clock value.

The second is an instant.

Always understand what the value means before selecting the type.

---

## 22. NUMERIC

Use:

```sql
NUMERIC
```

when exact decimal arithmetic matters.

Example:

```sql
amount NUMERIC(12, 2) NOT NULL
```

This is commonly appropriate for monetary values.

Choose precision and scale according to the real business domain.

---

## 23. Why Not Floating Point for Money?

Floating-point types use approximate binary representation.

For exact financial values, prefer an exact decimal representation such as:

```sql
NUMERIC(12, 2)
```

Use floating point where approximation is acceptable.

---

## 24. Phone Numbers Are Text

A phone number is an identifier, not a quantity.

Prefer:

```sql
phone TEXT
```

rather than:

```sql
phone BIGINT
```

This preserves values such as:

```text
+
leading zeros
formatting
```

according to the application's representation rules.

---

## 25. Postal Codes Are Usually Text

Postal codes can contain:

```text
leading zeros
letters
spaces
```

depending on the country.

Therefore:

```sql
postal_code TEXT
```

is often more appropriate than:

```sql
postal_code INTEGER
```

Model meaning, not appearance.

---

## 26. Business Codes Are Text

Example:

```text
INV-000123
```

should normally be:

```sql
invoice_code TEXT
```

It is an identifier, not a quantity.

---

## 27. JSONB

PostgreSQL supports:

```sql
JSONB
```

for flexible JSON data.

Example:

```sql
metadata JSONB
```

Useful cases include:

```text
flexible metadata
external payload fragments
provider-specific attributes
event payloads
```

It should not replace normal relational columns for core business data.

---

## 28. Normal Columns vs JSONB

If every order has:

```text
status
total
created_at
```

use:

```sql
status TEXT NOT NULL
total NUMERIC(12, 2) NOT NULL
created_at TIMESTAMPTZ NOT NULL
```

Do not hide fundamental fields inside JSONB.

Normal columns are easier to:

```text
constrain
index
join
query
document
```

---

## 29. Good JSONB Example

```sql
CREATE TABLE events (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    event_type TEXT NOT NULL,
    payload JSONB NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

Here the payload can genuinely vary by event type.

That is a stronger JSONB use case.

---

## 30. ARRAY

PostgreSQL supports arrays:

```sql
tags TEXT[]
```

Arrays can be appropriate for small, self-contained collections.

Before using one, ask:

```text
Do values need independent rows?
Do they need foreign keys?
Do they need separate constraints?
Will they be queried frequently?
```

If yes, a child table may be better.

---

## 31. ARRAY vs Relationship

If tags are full entities with:

```text
id
name
metadata
relationships
```

a relational model is usually clearer:

```text
products
tags
product_tags
```

Do not use arrays as a replacement for relationships automatically.

---

## 32. NULL Is a Schema Decision

A nullable column means absence is allowed.

Optional:

```sql
phone TEXT
```

Required:

```sql
phone TEXT NOT NULL
```

Do not make every field nullable simply because the application currently does not always provide it.

---

## 33. NOT NULL Is a Data Contract

Example:

```sql
email TEXT NOT NULL
```

This tells the database:

> Every user row must have an email value.

Application validation can provide friendly errors, but the database still protects the invariant.

---

## 34. DEFAULT

A default supplies a value when INSERT omits the column.

Example:

```sql
active BOOLEAN NOT NULL DEFAULT true
```

Then:

```sql
INSERT INTO users (name)
VALUES ('Agus');
```

produces:

```text
active = true
```

---

## 35. DEFAULT Is Not NOT NULL

Compare:

```sql
active BOOLEAN DEFAULT true
```

and:

```sql
active BOOLEAN NOT NULL DEFAULT true
```

The first can still accept explicit NULL.

The second cannot.

If the domain requires a value, use `NOT NULL`.

---

## 36. Good Defaults

Good defaults often represent natural creation behavior:

```sql
created_at TIMESTAMPTZ NOT NULL DEFAULT now()
active BOOLEAN NOT NULL DEFAULT true
```

Avoid defaults that hide missing required information.

For example:

```sql
name TEXT NOT NULL DEFAULT ''
```

may create fake valid-looking data.

---

## 37. Avoid "Everything TEXT"

Weak schema:

```text
id TEXT
active TEXT
price TEXT
created_at TEXT
```

Stronger schema:

```text
id → BIGINT / UUID
active → BOOLEAN
price → NUMERIC
created_at → TIMESTAMPTZ
```

The database can enforce meaningful behavior when the types are correct.

---

## 38. Avoid "Everything Nullable"

If the domain requires:

```text
name
email
created_at
```

then represent that:

```sql
name TEXT NOT NULL,
email TEXT NOT NULL,
created_at TIMESTAMPTZ NOT NULL
```

Nullability should describe the domain.

---

## 39. Consistent Identifier Types

If:

```sql
users.id BIGINT
```

then:

```sql
orders.user_id BIGINT
```

should normally use a compatible type.

Consistent types simplify:

```text
foreign keys
joins
application code
migrations
```

---

## 40. Example: Users

```sql
CREATE TABLE users (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name TEXT NOT NULL,
    email TEXT NOT NULL,
    active BOOLEAN NOT NULL DEFAULT true,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

Interpretation:

```text
one row
→ one user

id
→ generated identifier

name
→ required text

email
→ required text

active
→ required two-state flag

created_at
→ creation instant

updated_at
→ lifecycle timestamp
```

---

## 41. Example: Products

```sql
CREATE TABLE products (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name TEXT NOT NULL,
    price NUMERIC(12, 2) NOT NULL,
    active BOOLEAN NOT NULL DEFAULT true,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

The schema communicates the intended meaning directly.

---

## 42. Example: Orders

```sql
CREATE TABLE orders (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    user_id BIGINT NOT NULL,
    status TEXT NOT NULL,
    total NUMERIC(12, 2) NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

The relationship constraint will be added in the next material.

---

## 43. Mapping to Go

Typical conceptual mappings:

```text
BOOLEAN
→ bool

BIGINT
→ int64

TEXT
→ string

TIMESTAMPTZ
→ time.Time

UUID
→ UUID/string representation

NUMERIC
→ appropriate exact decimal representation
```

Exact mappings depend on the driver/library.

The important rule is preserving semantics.

---

## 44. NUMERIC Across the Application Boundary

Be careful when mapping:

```sql
NUMERIC
```

to floating-point types.

For money, preserve the exactness expected by the database.

Possible application strategies:

```text
decimal library
integer minor units
driver-supported numeric representation
```

Choose deliberately.

---

## 45. Time Across the Application Boundary

For:

```sql
TIMESTAMPTZ
```

a common Go representation is:

```go
time.Time
```

But the application still needs clear rules for:

```text
storage
API serialization
display timezone
reporting timezone
```

The database type alone does not define all application timezone behavior.

---

## 46. Schema and API Contracts

Schema decisions affect APIs.

For example:

```sql
email TEXT NOT NULL
```

means creating a user without an email must fail.

Likewise:

```sql
price NUMERIC(12, 2)
```

defines how the database represents the amount.

Schema and API design should agree on domain rules.

---

## 47. Schema Evolution

Production schemas change.

Example:

```sql
ALTER TABLE users
ADD COLUMN phone TEXT;
```

Adding a nullable column is often straightforward.

Changing an existing column to `NOT NULL` requires verifying existing data first.

Production migrations should consider:

```text
existing rows
application compatibility
deployment order
locking
migration duration
recovery strategy
```

---

## 48. Backward-Compatible Changes

During deployment, old and new application versions may temporarily coexist.

A common pattern is:

```text
add new column
↓
deploy code that understands it
↓
backfill if needed
↓
switch reads/writes
↓
add stronger constraints later
```

The exact migration depends on the workload.

---

## 49. Data Types and Performance

Type choice can affect:

```text
storage
indexes
comparisons
network transfer
application conversion
```

But correctness comes first.

Use this priority:

```text
correct meaning
→ integrity
→ consistency
→ performance optimization
```

Do not micro-optimize types before understanding the actual workload.

---

## 50. Core Design Questions

For every column, ask:

```text
What does it mean?

Can it be NULL?

What values are valid?

Is there a meaningful default?

Does precision matter?

Does timezone matter?

Is it an identifier or quantity?

Will it be queried?

Will it be joined?

Does it need a constraint?
```

These questions are more valuable than memorizing every PostgreSQL type.

---

## 51. Common Mistake: VARCHAR(255) Everywhere

Bad reasoning:

```text
"All strings are VARCHAR(255)."
```

Better:

```text
Use TEXT unless a meaningful limit exists.
```

If a real limit exists, enforce it intentionally.

---

## 52. Common Mistake: Float for Money

Avoid:

```sql
price DOUBLE PRECISION
```

when exact monetary representation is required.

Prefer:

```sql
price NUMERIC(12, 2)
```

or another domain-appropriate exact representation.

---

## 53. Common Mistake: Numeric Phone Number

Avoid:

```sql
phone BIGINT
```

Prefer:

```sql
phone TEXT
```

Phone numbers are identifiers.

---

## 54. Common Mistake: Nullable Boolean for a Simple Flag

Instead of:

```sql
active BOOLEAN
```

prefer:

```sql
active BOOLEAN NOT NULL DEFAULT true
```

when only two states exist.

---

## 55. Common Mistake: JSONB for Core Business Fields

Avoid putting:

```text
status
total
user_id
created_at
```

inside a JSONB object when those fields are fundamental.

Use normal columns.

JSONB should solve flexibility requirements, not replace schema design.

---

## 56. Common Mistake: Array Instead of Relationship

If values need:

```text
foreign keys
independent lifecycle
constraints
frequent queries
```

a separate table is often more appropriate than an array.

---

## 57. Common Mistake: Inconsistent ID Types

Avoid:

```text
users.id       → BIGINT
orders.user_id → TEXT
```

when both represent the same identifier.

Keep related types compatible.

---

## 58. Common Mistake: Fake Defaults

Avoid:

```sql
name TEXT NOT NULL DEFAULT ''
```

if an empty name is not a legitimate value.

Defaults should represent actual domain defaults.

---

## 59. Common Mistake: Timestamp Without Semantics

Do not choose `TIMESTAMP` just because the API calls a field:

```text
datetime
```

Determine whether it represents:

```text
calendar date
local wall-clock time
instant in time
```

Then choose the appropriate type.

---

## 60. Common Mistake: Designing From JSON Alone

An API payload might contain:

```json
{
  "price": "100.50",
  "active": "true"
}
```

That does not mean the database should store both as text.

API serialization and database representation are different concerns.

---

## 61. Production Checklist

Before creating a table:

```text
□ What does one row represent?
□ Are table and column names clear?
□ Does each column have the correct domain type?
□ Are required fields NOT NULL?
□ Are defaults meaningful?
□ Are IDs generated consistently?
□ Are related identifier types compatible?
□ Are timestamps modeled with correct timezone semantics?
□ Are monetary values represented exactly?
□ Are identifiers stored as identifiers rather than quantities?
□ Is JSONB actually needed?
□ Is ARRAY actually appropriate?
□ Could a relational table model the data better?
□ Are core business fields explicit?
□ Does the schema map cleanly to application code?
□ Can the schema evolve safely?
□ Are type choices driven by domain meaning rather than habit?
```

---

## 62. Practical Mental Model

Think:

```text
Domain concept
      ↓
One row = one thing
      ↓
Columns = properties
      ↓
Data types = meaning
      ↓
NULL/defaults = optionality + lifecycle
      ↓
Constraints = integrity
      ↓
Indexes = access patterns
```

This material focuses mainly on the first five layers.


---

## 64. What to Remember

1. A table should represent a clear domain concept.
2. Define what one row represents before defining columns.
3. Choose types based on meaning, not appearance.
4. `TEXT` is practical for many strings.
5. Do not add arbitrary `VARCHAR(255)` limits.
6. Use `BOOLEAN` for genuine two-state values.
7. Use `DATE` when only a calendar date matters.
8. Use `TIMESTAMPTZ` for values representing instants in time.
9. Use `NUMERIC` when exact decimal semantics matter.
10. Phone numbers, postal codes, and business codes are usually identifiers, not quantities.
11. Identity columns are a modern PostgreSQL option for generated numeric IDs.
12. UUIDs are useful when their architectural properties fit the system.
13. `NOT NULL` expresses a real required-data invariant.
14. `DEFAULT` should represent a legitimate default.
15. JSONB is useful for genuinely flexible data, not core relational fields.
16. Arrays are useful for some domains but should not automatically replace relationships.
17. Keep related identifier types compatible.
18. Application validation and database constraints solve different problems.
19. Schema changes must account for existing data and deployment compatibility.
20. A good schema makes invalid states harder to represent.
